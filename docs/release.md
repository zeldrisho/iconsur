# Release guide

Versioning is driven by git-cliff over conventional commits. The git-cliff integration is planned (item 3 in `docs/plan.md`); until it lands, the legacy `.github/workflows/build.yml` is the only automation.

## Version calculation (git-cliff)

- Breaking change → major
- `feat` → minor
- `fix`, `perf`, `revert` → patch
- `docs`, `refactor`, `test`, `build`, `ci`, `chore` appear in release notes when bundled with a release but never trigger one

Tag format is `v<version>` (single package, no component prefix).

## Release invariants

- `CHANGELOG.md` is generated by git-cliff — never hand-edit it. Fix commit messages or `cliff.toml` instead.
- Keep `package.json` version, tag, GitHub release, npm version, and changelog synchronized.
- A push to `main` containing only docs/chore/refactor commits does not create a release.
- Do not merge feature branches that already carry a bumped `package.json` version; let git-cliff propose the version and changelog.
- Before implementation, run `git fetch --prune`, inspect local and upstream state, and start from the latest target branch without discarding uncommitted work.
- Rebase work branches onto their target; never merge the target branch into them.

## Target release procedure (once git-cliff lands)

1. Write conventional commits, open a PR, run `vp check` / `vp test`.
2. Merge the PR to `main`.
3. The release workflow (`.github/workflows/release.yml`, planned) fetches complete tag history → runs git-cliff (compute version + changelog) → builds the binary (`pkg` or `vp pack`) → publishes `@zeldrisho/iconsur` to npm (first publish needs `--access public`) → creates a GitHub release with `dist/iconsur` attached.
4. Verify: npm version and dist-tag, `v<version>` tag, GitHub release asset, changelog entry.

Escalation: pause and investigate (do not manually patch) if npm, GitHub, tags, manifests, or changelogs disagree; if auth/OIDC/provenance fails; or if any step would rewrite a merged, tagged, or published commit.

## Legacy pipeline (current)

`.github/workflows/build.yml` runs on every push to `main`:

1. `npm install` (Node 10.x, inherited from upstream; moves to `pnpm install` via `vp` with the git-cliff workflow)
2. `npm run build` — `pkg . --targets node16-macos-x64 --output dist/iconsur`
3. `pascalgn/npm-publish-action` publishes to npm
4. `nyaascii/package-version` reads the version → `actions/create-release` creates the GitHub release → `actions/upload-release-asset` attaches the binary

This is the 2020-era flow and will be replaced by the git-cliff workflow.

## Known issues

- npm `latest` is `1.7.0` (May 2022); the fork's first release publishes the new `@zeldrisho/iconsur` scoped name.
- Homebrew formula is deprecated (upstream archived) and disabled 2027-02-01; see `docs/plan.md` item 7.
- Only `node16-macos-x64` binary target exists; arm64 untested.
- CI runs on `ubuntu-latest` and cannot exercise `set`/`cache` (macOS + privileged); smoke-test locally before releasing.
